1 Introduction

1.1 Purpose

This Software Requirements Specification (SRS) document describes the complete functional and non-functional requirements for a Pathology Laboratory Information Management System (LIMS). This document serves as the primary agreement between the development team and the client regarding what the system shall do.

1.2 Scope

The system is a B2B web-based platform designed for pathology labs, diagnostic centres, and hospital laboratory departments. It will manage the complete lifecycle of laboratory operations:

  • Patient registration and record management
  • Test ordering, sample collection, and barcode-based tracking
  • Result entry by technicians with doctor/pathologist validation
  • Automated report generation (PDF) and multi-channel delivery (SMS, WhatsApp, Email)
  • Billing, invoicing, and payment management (GST-compliant)
  • Inventory and reagent stock management
  • Role-based access control with 6 predefined roles
  • Real-time dashboard and business analytics
  • Complete audit trail of all system actions

Delivery Model: The platform shall be offered as a SaaS (cloud-hosted) product with optional on-premise and hybrid deployment for enterprise clients.

2 Overall Description

2.1 Product Perspective

This is a new, self-contained product (not an enhancement of an existing system). It is a web-based application accessible via modern browsers on desktops, tablets, and mobile devices. The system shall operate independently but provide RESTful APIs for integration with external systems such as HMS/HIS, lab equipment interfaces, and government reporting portals.

2.4 Assumptions & Dependencies

  • Users have access to a modern browser (Chrome, Edge, Firefox, Safari — latest 2 versions)
  • Internet connectivity is required for SaaS deployment; offline mode is available only in hybrid deployment
  • SMS/WhatsApp delivery requires integration with a third-party gateway (e.g., MSG91, Twilio)
  • Barcode label printing requires a compatible thermal printer connected to the workstation
  • The client shall provide lab-specific branding assets (logo, letterhead, signatures) for report templates
  • GST/tax configuration is specific to Indian regulatory requirements

4 Functional Requirements

Each functional requirement is identified with a unique ID in the format FR-MODULE-NNN along with its priority level.

MOD-01 User Management & Authentication

Handles user registration, login/logout, password management, session handling, and role assignment.

Req ID Requirement Description Priority
FR-AUTH-001 User Login System shall allow users to login via email/phone and password. On success, issue a JWT access token (15 min) and a refresh token (7 days stored as httpOnly cookie). HIGH
FR-AUTH-002 Token Refresh System shall allow token refresh using a valid refresh token. Old refresh token shall be revoked and a new pair issued (rotation). HIGH
FR-AUTH-003 Logout System shall invalidate the refresh token on logout and clear the httpOnly cookie. HIGH
FR-AUTH-004 Forgot Password System shall send a password reset link via email. Link shall expire in 30 minutes. HIGH
FR-AUTH-005 Account Lockout System shall lock user account after 5 consecutive failed login attempts for 30 minutes. HIGH
FR-AUTH-006 User CRUD Super Admin and Admin shall be able to create, view, update, and deactivate user accounts with role assignment. HIGH
FR-AUTH-007 Password Policy Passwords shall be minimum 8 characters with at least 1 uppercase, 1 number, and 1 special character. MEDIUM

MOD-02 Patient Registration

Manages patient onboarding with unique identification, demographics, and visit history tracking.

Req ID Requirement Description Priority
FR-PAT-001 UHID Generation System shall auto-generate a unique UHID for every new patient upon registration. HIGH
FR-PAT-002 Patient Demographics System shall capture: first name, last name, date of birth, gender, phone (required), email, address, blood group. HIGH
FR-PAT-003 Patient Search System shall provide instant search by name, phone number, or UHID with autocomplete suggestions. HIGH
FR-PAT-004 Visit History System shall display all previous orders, test results, and billing history for a patient in chronological order. MEDIUM
FR-PAT-005 Referring Doctor System shall allow linking a referring doctor to each patient visit/order. MEDIUM
FR-PAT-006 Duplicate Detection System shall check for duplicate patients by phone number and warn the operator before creating a new record. MEDIUM

MOD-03 Test Catalogue Management

Maintains the master list of all available laboratory tests with pricing, normal ranges, sample types, and package groupings.

Req ID Requirement Description Priority
FR-TST-001 Test Master CRUD System shall allow Admin to create, update, and deactivate tests with fields: name, code, category, price, normal range, unit, method, sample type, TAT. HIGH
FR-TST-002 Test Categories Tests shall be organised into categories (e.g., Haematology, Biochemistry, Microbiology, Serology, Histopathology). HIGH
FR-TST-003 Test Packages System shall support creating test packages/profiles (e.g., "Full Body Checkup" = CBC + LFT + KFT + Thyroid Panel) with combined pricing. MEDIUM
FR-TST-004 Normal Range Config Normal ranges shall be configurable per test with support for age-wise and gender-wise variations. MEDIUM
FR-TST-005 Test Search System shall provide searchable test selection with code or name autocomplete during order creation. HIGH

MOD-04 Order & Sample Tracking

Manages the complete lifecycle of test orders from creation through sample collection to final result delivery.

Req ID Requirement Description Priority
FR-ORD-001 Order Creation System shall allow creating an order for a registered patient with one or more tests/packages. Auto-generate a unique order number. HIGH
FR-ORD-002 Order Status Lifecycle Each order shall move through statuses: REGISTERED → SAMPLE_COLLECTED → PROCESSING → COMPLETED → DELIVERED. Status updates shall be timestamped. HIGH
FR-ORD-003 Barcode Generation System shall generate a unique barcode for each sample and support printing on thermal printers. HIGH
FR-ORD-004 Technician Assignment System shall allow assigning specific orders/samples to a lab technician. MEDIUM
FR-ORD-005 TAT Tracking System shall track turnaround time per order and highlight orders that exceed the configured TAT threshold. MEDIUM
FR-ORD-006 Order Search & Filter System shall provide search and filter by order number, patient name, status, date range, and assigned technician. HIGH

MOD-05 Result Entry & Validation

Enables lab technicians to enter test results and pathologists to validate them before report release.

Req ID Requirement Description Priority
FR-RES-001 Result Entry Lab Technician shall enter results for each test in an order. Support both numeric (quantitative) and text (qualitative: Positive/Negative/Reactive) values. HIGH
FR-RES-002 Abnormal Flagging System shall automatically flag results as abnormal (HIGH/LOW) if the value falls outside the configured normal range. HIGH
FR-RES-003 Doctor Validation Results shall require validation/approval by a Doctor/Pathologist before the report can be generated and released. HIGH
FR-RES-004 Remarks Technician and Doctor shall be able to add remarks/comments to individual test results. MEDIUM
FR-RES-005 Amendment History If a result is edited after initial entry, system shall maintain a complete amendment history with old value, new value, who changed it, and when. HIGH

Auto-generates branded PDF reports and delivers them to patients through multiple channels.

FR-RPT-002 Branded Templates Report templates shall be configurable per lab/branch with custom branding (logo, colours, footer text). HIGH
FR-RPT-003 SMS Delivery System shall send an SMS to the patient's phone with a secure link to download the report. HIGH

FR-RPT-006 QR Code Verification Each report shall contain a QR code that links to a verification page confirming the report's authenticity. LOW
FR-RPT-007 Reprint / Re-deliver Authorised users shall be able to reprint or re-send a report at any time. MEDIUM

Tracks lab consumables, reagents, and supplies with stock level alerts and expiry monitoring.

FR-INV-001 Item Master System shall maintain an inventory master with: item name, SKU, unit of measure, current stock, minimum stock level, supplier details. MEDIUM

7 Non-Functional Requirements

7.1 Security Requirements

Req ID Requirement Description Priority
NFR-SEC-001 HTTPS Encryption All client-server communication shall be encrypted using TLS 1.2+ (preferably TLS 1.3). HTTP requests shall be redirected to HTTPS. HSTS headers shall be enforced. HIGH
NFR-SEC-002 Password Hashing All passwords shall be hashed using bcrypt with a minimum of 12 salt rounds. Plaintext passwords shall never be stored or logged. HIGH
NFR-SEC-003 JWT Security Access tokens shall be signed using RS256 (asymmetric). Refresh tokens shall be stored in httpOnly, Secure, SameSite=Strict cookies. Token rotation on every refresh. HIGH
NFR-SEC-004 SQL Injection Prevention All database queries shall use parameterised queries via the ORM. No raw SQL shall be used unless explicitly parameterised. HIGH
NFR-SEC-005 XSS Prevention Content-Security-Policy headers shall be set via Helmet.js. All user inputs shall be sanitised. React's default escaping shall be relied upon for output encoding. HIGH
NFR-SEC-006 CORS Policy CORS shall be configured to allow requests only from the whitelisted frontend domain(s). Credentials shall be allowed only for the configured origin. HIGH
NFR-SEC-007 Rate Limiting API rate limiting: 100 requests per 15 minutes for general endpoints. 10 requests per 15 minutes for authentication endpoints. HIGH
NFR-SEC-008 Input Validation All API request payloads shall be validated against Zod schemas. Invalid requests shall return 400 Bad Request with descriptive error messages. HIGH
NFR-SEC-009 Audit Trail Every CUD (Create, Update, Delete) operation shall be logged with user identity, timestamp, IP address, and data diff (as defined in MOD-10). HIGH
NFR-SEC-010 Data Backup Automated daily database backups with 30-day retention. Point-in-time recovery capability. Backups shall be encrypted at rest. HIGH

8 Deployment & Infrastructure

8.1 Deployment Models

Model Description Target Client Infrastructure
Cloud SaaS Fully managed by the vendor. Multi-tenant architecture. Client accesses via browser. Small to medium labs, single-branch operations AWS / Azure / GCP, managed PostgreSQL, Nginx LB, CDN, auto-scaling
On-Premise Deployed on client's own servers. Full data sovereignty. Single-tenant. Hospital labs, enterprise clients with compliance requirements Docker Compose, PM2 cluster (4 workers), local PostgreSQL, Nginx, Redis
Hybrid Central cloud + local edge nodes at branches. Data syncs in real-time. Multi-branch diagnostic chains (5+ locations) Cloud central + Docker per branch, sync via API, offline-capable

8.2 Load Balancing Architecture

The production deployment shall use the following load balancing configuration:

  • Nginx acts as the reverse proxy and load balancer at the gateway layer
  • Traffic distribution uses the least-connection algorithm for even load distribution
  • Health checks ensure requests are only routed to healthy Node.js instances
  • SSL termination happens at Nginx — backend instances communicate over HTTP internally
  • PM2 cluster mode spawns 4 Node.js worker processes (configurable per CPU cores)
  • Static assets (React build output) are served directly by Nginx with cache headers
  • API requests (/api/*) are proxied to the Node.js cluster

10.2 API Standards

  • Authentication: Bearer token in Authorization header for all protected endpoints
  • Pagination: All list endpoints support ?page=1&limit=20 query parameters
  • Sorting: ?sortBy=createdAt&order=desc
  • Filtering: Module-specific query parameters (e.g., ?status=PROCESSING&dateFrom=2026-01-01)
  • Error Format: { "success": false, "message": "...", "errors": [...] }
  • Success Format: { "success": true, "data": {...}, "meta": { "page": 1, "total": 50 } }

# Deliverable Description
1 Source Code Complete frontend (React) and backend (Node.js) source code in a Git repository
2 Database Schema Prisma schema file with all migrations
3 API Documentation Swagger/OpenAPI specification for all endpoints
4 Deployment Package Docker Compose files, Nginx configs, PM2 ecosystem config
5 User Manual End-user documentation for each role
6 Admin Guide System administration and configuration guide
7 Test Reports Unit test and integration test results with coverage report

11.2 Acceptance Criteria

  • All functional requirements marked as HIGH priority shall be fully implemented and tested
  • All 6 user roles shall be functional with correct permission enforcement
  • The complete lab workflow (Registration → Order → Sample → Result → Validation → Report) shall work end-to-end
  • PDF report generation shall complete within 3 seconds
  • API response times shall meet the targets defined in Section 7.2
  • All security requirements (Section 7.1) shall be implemented and verified
  • The system shall be deployed and accessible on the agreed deployment model
  • No critical or high-severity bugs at the time of delivery
